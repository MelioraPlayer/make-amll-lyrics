# 占位、上传与 PR

## 授权和账号

用户说“创建占位”“提交到 AMLL”“可以，提交吧”时，属于相应 GitHub 操作授权；同一任务已授权就直接完成。只说“帮我打轴”“看看这份文件”时先本地完成，不自动上传 Gist、Issue 或 PR。创建 skill 本身不触发投稿。

默认使用 **GitHub 网页对应的 Issue Form 新建占位和投稿 Issue**，`gh` 负责查询、TTML Gist 上传及提交后的核验。这样沿用仓库模板及默认标签；创建后仍须核验实际结果。用户本次明确指定其他入口时遵循其要求，不把某种工具偏好说成仓库官方规定。

使用 gh 查询前核对 CLI 账号：

```powershell
gh auth status
gh api user --jq '{login,id}'
gh api repos/amll-dev/amll-ttml-db --jq '.permissions'
```

使用用户指定或已确认的账号。网页提交前还须核对浏览器实际登录账号；CLI 与浏览器不一定使用同一账号。若账号不符，先查可用登录信息，不打印令牌，不擅自修改 SSH/Git 认证配置。多个账号且意图不明时才询问选择。

## 新建 Issue 的入口与标签

1. 先查重并确认没有可复用的本人占位、投稿 Issue 或 PR，再从仓库网页的 New issue 入口选择对应模板。
2. 占位使用“歌词制作占位”表单（`process-lyric.yml`）；投稿使用“提交/补正歌词”表单（`submit-lyric.yml`）。读取当前模板，保留其默认标签并填写表单，不能用空白 Issue 或复制模板正文替代 Issue Form。
3. 用户已授权占位或投稿时直接完成网页提交；创建后读回编号、正文、作者和实际 labels，不能把模板预设标签当成已经成功应用。
4. 网页不可用时保留准备好的内容并说明具体阻塞，不擅自改用已知会丢标签的 `gh issue create` 或 POST Issues API。

**权限已知时不要重复失败路线**：非协作者通过 gh/API 创建 Issue 时，传入的 labels 可能被静默忽略；事后 `gh issue edit --add-label` 也可能返回 `AddLabelsToLabelable` 权限错误。已在当前账号确认该限制时，不再走“CLI 创建 → 再补标签”的路线，也不要把 API 编辑权限限制推断为网页模板创建时必然无法应用默认标签。网页模板实际结果以提交后核验为准。

**已有记录的处理**：缺标签时保留现有 Issue 和关联关系。歌词已经投稿或生成 PR 后，不为了标签创建第二个占位、第二个投稿或第二个 PR，也不先关闭旧记录再另建。不能切换账号绕过权限；没有授权不另发评论请求维护者补标签。标签缺失本身不代表投稿失败，核对当前工作流和 PR 状态即可。[GitHub API 的标签权限说明](https://docs.github.com/en/rest/issues/issues#create-an-issue)

## 占位

查重完成后，读当下的 `process-lyric.yml`。复用用户现有占位，保存 issue 编号，正文注明歌曲版本、ID、链接。标题为 `[歌词制作占位] 歌手 - 歌名`，待做项列表按模板；别拿某首歌的历史编号作为下一首的固定编号。

可先用 UTF-8 文本文件准备正文，再填入网页“待做歌曲列表”字段，按上一节完成创建和标签核验。

缺失占位分类标签不会自动阻断已创建 PR 的流程；若用户担忧，读真实 PR 状态和当前工作流再回答，不保证维护者何时审核。

## 投稿前冻结

**先确认用户已完成最终复核。** 本 skill 是制作辅助，不对最终质量作保证；用户须对照正确音源从头到尾试听，逐句检查原文、译文、时间、拆音节、背景／对唱和元数据。只有自动模型、结构检查或机器人成功的证据时，仍应交付待复核稿，不能直接投稿。记录对话中用户实际给出的复核确认，不伪造试听记录；已明确确认并授权的，不再重复询问。后续有改动则重新检查受影响部分。

1. 对最终用户修订与投稿文件做语义比较；检查译文、Ohh、对唱和新拆词都在。
2. 运行本地检查和官方 parser，写入文件 hash、歌曲 ID、账号 ID、占位编号及验证结果。
3. 重新查询是否出现同曲 PR，避免长时间制作后与新投稿撞车。
4. 读当前 `submit-lyric.yml` 与 `check-submit.yml`。当前常用路径是“投稿 Issue → 机器人校验 → 自动 PR”，不额外手建第二个 PR。

## 上传直链与创建投稿 Issue

上传单个 TTML 到用户允许的存储；本流程可使用 secret Gist 得到可匿名读取的 raw URL。secret 仅不公开列出，放到公开 Issue 后链接对外可见。Gist 中不放音频、模型、原始私人文件或整个工作目录。

```powershell
gh gist create 'work/song/submission/final.ttml' --desc 'AMLL TTML 投稿'
```

从返回 URL 获取 gist ID，用 `gh api gists/ID` 取得实际 raw_url。不要从 history SHA 猜 raw blob 路径。下载 raw_url 再做 SHA-256 对比。结果未知时先查账号的近期 Gist/Issue，避免重试造成重复外部记录。

在网页打开当前投稿 Issue Form，填写以下字段；可事先将内容保存为 UTF-8 文本供填表核对：

- TTML 歌词文件下载直链。
- 提交缘由：新歌词提交或修正已有歌词。
- 阅读规范的确认（代理确实读过并检查后才填写）。
- 备注：关联占位、准确版本/平台 ID、提交内容。不要放闲聊、无关说明或虚假的“逐句试听/百分之百对齐”。

标题按实际写 `[歌词提交]`、`[歌词补充]`、`[歌词更正]` 或 `[歌词补正]`，不能为了通过检查都写新投稿。修正保留原作者并指向原 PR；按当前 Wiki 核查补正冷却周期。

通过网页提交一次后，用 gh 读回 body、author、title 和 labels，并保存真实 Issue URL。结果未知时先查询近期 Issue，不能直接再次点击提交或改走 CLI 再建一份。若仍缺标签，按“已有记录的处理”继续核验实际工作流，不重建。

## 等待机器人并核对 PR

使用 `gh run list --workflow check-submit.yml` 找到对应标题/时间的运行，保存 run ID；用 `gh run watch RUN_ID --interval 10 --exit-status` 或有间隔的状态检查等待。不能每秒轮询，不把只有普通环境警告的成功运行报成失败。

失败先看日志和机器人评论，修正明确原因；同一个失败不盲目重复投稿。正在编译不代表卡死。任务内完成这一轮状态检查，不自动设长期监控。

当机器人生成 PR：

1. 从评论/搜索得到真实 PR URL；通过 `gh pr view` 检查关联投稿 Issue、作者署名、占位链接、文件列表、head SHA。
2. 只有一个 TTML 变更或与用户意图一致的文件集合；不能夹带音频、临时脚本、旧稿。
3. 按精确 head SHA 下载 PR 文件，使用官方 parser 回读，与冻结稿比较原文/译文/时间/声部。机器人重序列化后仍可能丢失不兼容的 metadata，必须实际验收。
4. Codex 提供 `attach_artifact` 时将这个 PR 附到当前聊天。
5. 告知用户：账号、PR 链接、占位关联、机器人是否成功、当前人工审核状态。缺失 PR checks 不要说成所有 CI 通过；投稿工作流成功与 PR 检查是不同信息。

## 完成、关闭与后续修订

投稿 Issue 被机器人标记 completed 并锁定，常表示已交给 PR，不是审核拒绝。看 PR 是 OPEN/MERGED/CLOSED 及 reviews 的真实结果。

占位通常待审核通过再关闭；不要在自动校验成功时提前宣告入库。对审核意见逐条修订，并按当下机器人支持的更新方式修改同一投稿，不重复提交多个 PR。没有用户授权时不评论催审；需要提醒/持续跟踪时由用户明确提出再建立自动化。
